# Checks and coverage

What the UVC checks on your behalf, what it publishes for you to check, and what
it measures.

## Protocol assertions

`src/axi_lite_if.sv` carries **49 concurrent assertions** drawn from AMBA IHI
0022 — section A3.2 (handshake), A3.3 (channel dependencies), A3.4 (responses)
and section B (the AXI4-Lite subset).

They live in the interface rather than in the monitor on purpose. An assertion in
the interface sees the wires, so it polices the UVC and the DUT equally:
whichever side drives the signal that breaks a rule is the side the failure
points at. A check that only ever validates the DUT will not catch the day your
driver is the one at fault.

### What is checked

| Group | Rules | Count |
| --- | --- | --- |
| **VALID held until READY** | Once asserted, VALID stays high until the handshake completes — AWVALID, WVALID, BVALID, ARVALID, RVALID | 5 |
| **Payload stable while stalled** | AWADDR, AWPROT, WDATA, WSTRB, BRESP, ARADDR, ARPROT, RDATA, RRESP cannot change while their VALID waits for READY | 9 |
| **Quiet during reset** | Every VALID is low while ARESETn is asserted | 5 |
| **Quiet on reset release** | Every VALID is low on the first ACLK edge after ARESETn rises | 5 |
| **Response ordering** | A B or R response only appears if a request is outstanding to justify it | 2 |
| **Legal encodings** | BRESP and RRESP are OKAY, SLVERR or DECERR — never EXOKAY, which AXI4-Lite has no exclusive access to earn | 2 |
| **No X on control** | All ten VALID/READY signals are known out of reset | 10 |
| **No X on payload** | AWADDR, AWPROT, WSTRB, ARADDR, ARPROT, BRESP, RRESP and RDATA are known when offered | 8 |
| **No X on WDATA, per lane** | one generated assertion per byte lane: an X fails only where WSTRB says the byte is actually being written | 1 (× `STRB_WIDTH` at elaboration) |
| **Address alignment** | AWADDR and ARADDR aligned to the data bus width (generated only when `ADDR_LSB > 0`) | 2 |
| | | **49** |

Two of these are worth calling out.

**WDATA X-checking is per byte lane.** An X in a byte lane WSTRB *disables* is
legal — nobody is going to use it. An X in a lane WSTRB *enables* is a real bug.
Checking the whole vector would have flagged the first; checking nothing would
have missed the second. So there is one assertion per lane, generated by a
`genvar` loop. RDATA gets no such treatment because a read has no strobe: every
bit of it is meaningful, so all of it must be driven.

**Response ordering is checked by counting handshakes**, because AXI4-Lite has
no transaction IDs to match on:

```systemverilog
property p_b_after_request;
  @(posedge aclk) disable iff (aresetn !== 1'b1 || !checks_enable)
    b_handshake |-> ((b_accepted < (aw_accepted + (aw_handshake ? 1 : 0))) &&
                     (b_accepted < (w_accepted  + (w_handshake  ? 1 : 0))));
endproperty
```

A write response is legitimate only if fewer responses have been accepted than
both address phases and data phases — which catches a slave answering a write it
was never given, and a slave answering before the write data arrived. The
`? 1 : 0` terms include a handshake completing on this very edge, which is the
legal zero-latency case.

### Turning checks off

Through the config (see [Configuration › Checks](configuration.md#checks-and-instrumentation)),
or directly on the interface for a testbench with no UVM in it:

```systemverilog
initial regs.configure(.en_checks(1), .en_addr_alignment(0), .en_exokay(1), .en_prot(1));
```

| Switch | Effect |
| --- | --- |
| `checks_enable` | master switch |
| `check_addr_alignment` | for a DUT that deliberately decodes sub-word addresses |
| `check_exokay` | for a link where EXOKAY is somehow expected |
| `has_prot` | for a DUT that ties AxPROT off |

Turning a check off to quieten a failure is turning off the thing that found the
bug. These exist for links whose conventions genuinely differ, not for triage.

### How failures reach UVM

The assertions know nothing about UVM. Each failure calls
`protocol_error(rule, msg)`, which prints, records the rule name in
`last_protocol_error_rule`, and increments `protocol_error_count`. The monitor's
`check_phase` turns a non-zero count into a `UVM_ERROR`, so a protocol violation
fails the test even though nothing in the assertion path imports `uvm_pkg`.

That also means a non-UVM testbench can use the interface and read the counter
itself — which is exactly what the checker's own testbench does.

### The assertions are tested

An assertion nobody has ever seen fail is a claim, not a check.

`tb/axi_lite_if_check_tb.sv` is a plain SystemVerilog testbench — no UVM — that
drives the interface directly through **17 scenarios** and requires each to
behave:

- 13 deliberate violations that must be **caught**: VALID withdrawn before its
  handshake, AWADDR changed while stalled, WDATA changed while stalled, an
  unaligned ARADDR, BRESP = EXOKAY, BVALID with no write requested, RVALID with
  no read requested, BVALID before the write data arrived, AWVALID asserted
  during reset, ARVALID high as reset releases, an X on AWVALID out of reset, an
  X in an enabled WSTRB lane, and more.
- 4 legal or excused scenarios that must stay **quiet**: a legally stalled write,
  an unaligned address with `check_addr_alignment` cleared, an X in a byte lane
  WSTRB disables, and a real violation with `checks_enable` cleared.

```bash
cd tb && make check-protocol
```

The last two matter as much as the violations: they prove the escape hatches
actually escape, so a project that legitimately needs one is not left wondering
whether the check is still half-live.

## The monitor's analysis ports

The monitor publishes on two ports, and picking the right one saves a class of
scoreboard bug.

| Port | Publishes | When |
| --- | --- | --- |
| `request_analysis_port` | a **clone** of the transaction | the moment it is fully requested — AW+W both seen, or AR seen |
| `item_analysis_port` | the transaction | at the B or R handshake, complete with `rdata` and `resp` |

```systemverilog
agent.monitor.item_analysis_port.connect(scoreboard.analysis_export);
// or, equivalently
agent.item_port().connect(scoreboard.analysis_export);
```

Use `item_analysis_port` for scoreboarding and coverage — it is what you want
nine times in ten. Use `request_analysis_port` when you need to know what went
*into* a DUT before it answers: feeding a reference model early, or checking a
bridge's input stream against its output stream.

The request port publishes a clone, not the live handle, so the completed
transaction arriving later on the other port cannot retroactively mutate what
your reference model already consumed.

The monitor publishes **regardless of role**, so a `UVM_PASSIVE` agent on a link
you do not drive still feeds your checks and your coverage.

### One ordered sampling loop

All five channels are sampled in a single loop per clock edge — requests first,
then responses — rather than in five parallel threads. Two channels handshaking
on the same edge would otherwise race, and the order your scoreboard saw could
change between runs of the same seed. Write pairing joins the AW and W queues
FIFO, which is the only ordering AXI4-Lite gives you without transaction IDs.

## Functional coverage

`axi_lite_coverage` is a `uvm_subscriber #(axi_lite_seq_item)` on the completed
stream, built automatically by the agent unless `coverage_enable` is cleared.

It carries **no width parameter**, so one coverage model aggregates across every
port in your testbench. Bus width is a coverpoint rather than something baked
into the type — which is what lets a 32-bit link and a 64-bit link contribute to
the same numbers.

| Coverpoint | Bins |
| --- | --- |
| `cp_kind` | read, write |
| `cp_resp` | okay, slverr, decerr, exokay |
| `cp_data_width` | 32, 64, other |
| `cp_addr_width` | narrow (1–16), 32, 64, other |
| `cp_strobe` | none, single, partial, full — **gated `iff` the item is a write** |
| `cp_privileged`, `cp_nonsecure`, `cp_instruction` | the three AxPROT bits, independently |
| `cp_latency` | immediate (0–2), quick (3–8), slow (9–32), very_slow (33–255), glacial (256+) |
| `cp_addr_stall`, `cp_resp_stall` | none, short×3, mid (4–15), long (16+) |
| `cp_addr_bucket` | the window split into 8 equal parts |

Plus crosses: kind × resp, kind × stall, kind × strobe (with reads excluded by
`ignore_bins`), and width combinations.

Two details that were bugs before they were features:

**`cp_strobe` is gated on writes.** Without the `iff`, every read landed in a
strobe bin and the numbers claimed coverage that half the traffic could not
possibly contribute to.

**`cp_addr_bucket` divides the window, not the address space.** The bucket is
`(addr - lo) / ceil(span/8)`, so a 12-bit peripheral aperture is split into eight
meaningful regions rather than all landing in bucket 0 of a 64-bit space.

Coverage is sampled on every run, but **no closure target has been set against
it**. It tells you what the stimulus reached; it does not yet tell you whether
that is enough.

## Running the tests

### The UVC's own self-test

Master and slave agents facing each other across a register slice, at five port
geometries in one snapshot: 32/32, 32/64, 64/64, 12/32 and 16/64.

```bash
cd tb
make                          # the default test
make TEST=axi_lite_sweep_test # a specific one
make regress                  # the protocol checker, then all eight tests
make waves                    # run and dump waves.wdb
make gui                      # interactive XSIM
```

| Test | Exercises |
| --- | --- |
| `axi_lite_smoke_test` | a little traffic, no backpressure |
| `axi_lite_multiwidth_test` | all five widths, random backpressure — **default** |
| `axi_lite_backpressure_test` | every built-in READY model, one per link |
| `axi_lite_no_ready_test` | every READY held low, then released |
| `axi_lite_sweep_test` | walk every location of every window |
| `axi_lite_error_resp_test` | SLVERR and DECERR regions in the slave model |
| `axi_lite_pipelined_test` | several transactions in flight at once |
| `axi_lite_reset_test` | ARESETn pulsed mid-traffic |

### The integration example

```bash
cd example
make                                  # random traffic in the register map
make TEST=example_directed_test
make regress                          # all five
```

| Test | Exercises |
| --- | --- |
| `example_base_test` | random traffic inside the register map |
| `example_backpressure_test` | burst backpressure and a bursty source |
| `example_directed_test` | named registers, including a byte-strobed write |
| `example_sweep_test` | walk every register in the map |
| `example_decerr_test` | half the traffic aimed outside the aperture |

### Reading the result

XSIM exits 0 even after a `UVM_FATAL` — the test called `$finish`, it did not
crash — so a script checking only the exit status will call a failing test a
pass. Both Makefiles grep the log for the top module's own banner instead:

```
============================================================
 UVM-TB SUMMARY  |  module: example_dut  |  top: example_tb_top
 test    : example_base_test
 result  : PASSED
 fatals=0 errors=0 warnings=0
============================================================
```

Copy that pattern into your own testbench top. It is the difference between CI
that reports failures and CI that reports green.

## What a passing run establishes

- Every transfer the UVC drove and every transfer the DUT drove obeyed the
  handshake, stability, reset, ordering and encoding rules — because the
  assertions watch the wires, not one side of them.
- The assertions themselves fire when they should and stay quiet when they
  should, on 17 scenarios.
- Five port geometries elaborated into one snapshot and were driven by one
  unparameterized sequence library.
- Every configured READY model produced the duty cycle it promised, measured by
  the slave driver's per-channel census (`AW 367/368 (99%)`).
- Requests arrived at the far side of the DUT in order and unmodified, responses
  came back matched to them, and read data matched a shadow model of the slave's
  memory — except where a concurrent write to the same address made the value
  genuinely unordered, which is tracked rather than assumed away.

What it does not establish: coverage closure (sampled, no target set), and
portability (only XSIM 2023.2 has ever compiled this code).
